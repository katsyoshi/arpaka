# Structural Tree（構造化構文木）提案設計（ドラフト）

## この文書の位置づけ

これは、Ruby フロントエンドに `Structural Tree` を導入するための設計ドラフト
である。実装済みの API、言語プラグインの登録方法、LSP のプロトコルを定義
する文書ではない。

Structural Tree は、式の細部まで保持する AST ではなく、manazashi が必要とする
粒度で Ruby の字句的な定義構造を取り出すための軽量な定義木とする。主な対象
は `class`、`module`、メソッドの宣言であり、深い構文・意味解析を行う詳細
AST の代替にはしない。

## 背景と目的

現在の Arpaka の詳細 AST は、`Program` を根に、リテラル、呼び出し、代入、
制御構文などを含む式・文の詳細を表す。これは構文や後段の AST 利用に必要な
情報を保持する表現であり、manazashi の定義ナビゲーションに必要な最小単位
を直接表すことを目的としていない。

詳細 AST からクラスやメソッドだけを利用側で探索すると、式の細部を走査する
実装が利用側へ漏れ、構文上の差異や定義の所属の扱いも各利用側で決めること
になる。Structural Tree は、こうした利用側の走査を減らし、定義と字句的な
包含関係を安定した形で取り出すために導入する。

ここで扱うのは定義の構造であり、参照解決、ローカルスコープ、実行時の意味、
動的に生成される宣言ではない。それらが必要な深い解析には、v2 の詳細 AST
を利用する。

## 詳細 AST と Structural Tree

| 観点 | 詳細 AST | Structural Tree |
| --- | --- | --- |
| 主な目的 | Ruby の構文・式・文を表す | manazashi 向けに字句的な定義構造を表す |
| 粒度 | 式、文、リテラル、呼び出しなど | `class`、`module`、インスタンスメソッド、singleton method など |
| 根 | `AST::Program` などの詳細 AST ルート | ソース単位の構造化ルート |
| 子要素 | 構文木上の式・文 | 字句的に含まれる定義ノード |
| 位置 | 詳細 AST の契約による | ファイル名や行などを持てるが、必須の形は未確定 |
| 式の詳細 | 保持する | 原則として保持しない |
| 参照・スコープ | 詳細解析の対象になり得る | 扱わない |

二つは排他的な正解ではない。`ast_type` などでどちらの表現を生成する場合
でも、生成フロントエンドのクラスのルートは同じであるべきである。たとえば
`--class-name MyParser` または `class_name: "MyParser"` を指定した場合、
詳細 AST でも Structural Tree でも生成物は `MyParser` をルートとする。AST の
種類ごとに利用側が別のルートクラス名を指定する設計にはしない。

## 構造化する対象

### 初期対象

初期実装では、次の定義を構造化ノードとして扱う。

- `class` 定義
- `module` 定義
- インスタンスメソッド定義
- singleton method 定義（`def self.foo` や `def obj.foo` など）

各ノードは概念的に、定義種別、名前、字句的な親、子ノードを持つ。ファイル
名や行などの位置情報を持てる設計は検討するが、フィールドの完全な形や、すべて
の入力で位置を提供できることはこのドラフトで要求しない。

```text
source
└── module A
    ├── class B < C
    │   ├── instance method new
    │   └── singleton method build
    └── method helper
```

この例では、`A`、`B`、`new`、`build`、`helper` を定義ノードとして扱い、
`A` と `B`、`B` と各メソッドの関係は字句的な包含として表す。式全体を子
ノードとして複製することは要件ではない。

### 名前と種別

`name` はソース上で定義を識別するための値とする。インスタンスメソッドと
singleton method はどちらもメソッドノードだが、singleton method であること
を区別できなければならない。一方、singleton method の種別値、所有者（`self`
や任意の式）の表現、インスタンスメソッドとの共通インターフェースの具体的な
形は未決定である。

親子関係と、名前を連結した表示用パスや完全修飾名は分けて扱える余地を残す。
字句的な所属を、Ruby の定数解決や実行時の所有者と同一視しない。

### 位置

ファイル名や行などの位置情報は、利用側にとって有用な場合があるため持てる
可能性を残す。ただし、位置は Structural Tree の必須要件ではなく、次を固定し
ない。

- ファイル名、行、列、バイト・文字オフセットのどれを提供するか
- 定義名の位置か、宣言全体の位置か
- すべてのノードで位置が利用できるか
- 不明または推定された位置をどう表すか

式の一つひとつを位置付きで保持することや、編集のための精密な source map は
Structural Tree の要件にしない。そうした情報が必要なら、詳細 AST や v2 の
詳細解析側で扱う。

## 継承と字句的包含

クラスの superclass は、定義に付随する継承情報として欲しい。これは字句的な
親子関係とは別の関係であり、同じ `children` に混ぜない。`class B < C` の `B`
と `C` を、ソース上の包含関係として扱うわけではない。

一方、`include`、`prepend`、`extend` などの mix-in は Structural Tree の対象外
とする。mix-in を含む継承・探索関係や、その名前解決まで必要な場合は、詳細
AST を利用する。superclass の具体的なフィールド名や、式として書かれた
superclass の扱いは未決定である。

## 詳細 AST との使い分け

Structural Tree は、詳細 AST の全式を再走査しなくても、定義とその字句的な親子
関係を得られるようにする。詳細 AST のノードへの相互参照や全式の対応表を
初期実装の要件にはしない。

次のように使い分ける。

1. 定義の一覧、字句的な包含、必要に応じた superclass を得るには Structural Tree
   を使う。
2. 動的な宣言、参照解決、ローカルスコープ、mix-in の解析、式の意味が必要な
   場合は v2 の詳細 AST を使う。
3. Structural Tree に不足する情報を、暗黙の推定で通常の定義や参照として追加
   しない。

## 決定事項／方針

このドラフトで固定する方針は次のとおりである。

- Structural Tree は、manazashi の粒度に合わせた軽量な字句的定義木であり、詳細
  AST とは別の出力表現とする。
- 初期対象は `class`、`module`、インスタンスメソッド、singleton method とする。
  singleton method はメソッドノードとして扱い、通常のインスタンスメソッドと
  判別できる情報を保持する。
- 定義の字句的な包含関係は、詳細な式 AST を再走査しなくても取得できるように
  する。superclass も表現するが、字句的な包含関係とは別の関係として扱う。
- `include`、`prepend`、`extend` などの mix-in、動的な宣言、参照、ローカル
  スコープは対象外とする。これらの深い解析が必要な場合は v2 の詳細 AST を
  利用する。
- ファイル名や行などの位置情報は任意とし、精密な位置や source map は要件に
  しない。
- 同じ class/module の reopen は宣言ごとの occurrence として保持し、生成時に
  単一の論理定義へ自動的にマージしない。consumer 側で必要に応じてマージする。
- `--class-name` / `class_name` は AST の種類にかかわらず、生成物の安定した
  ルートを指定する概念として維持する。
- LSP の document symbols や限定的な定義ジャンプは将来の利用例になり得るが、
  Structural Tree 自体の API や完全な参照検索を定義するものではない。言語
  プラグインの API、登録、検出、合成方法もこの設計では決めない。

## 未決事項

### ノードのフィールドスキーマ

名前、種別、字句的な親子関係、superclass をどの API 形・フィールドで公開するか
は未決定である。

### singleton method の所有者表現

singleton method の所有者を `self` や式として保持するか、`def obj.foo` の `obj`
をどこまで表現するかは未決定である。

### superclass 式の表現

式として書かれた superclass を、単純な名前、参照可能なノード、詳細 AST の式への
リンクのどれで表現するかは未決定である。

### 任意位置情報の形式

任意の位置情報について、`Location` の形、範囲の端点、エンコーディング、不明値の
表現をどうするか、位置を持たない入力をどう扱うかは未決定である。

### consumer occurrence 識別子

consumer が occurrence を識別し、必要に応じて論理定義へマージできるように、どの
識別情報をどこまで提供するかは未決定である。

## 実装へ進む際の確認項目

実装着手時には、まず小さな Ruby ソース集合で次を確認する。

- class/module/インスタンスメソッド/singleton method の宣言をノード化できる
  こと。
- singleton method が通常のインスタンスメソッドと区別できること。
- 字句的な親子関係と superclass の関係を混同せずに保持できること。
- 同一名の reopen を occurrence として保持し、consumer 側でのマージを妨げ
  ないこと。
- `--class-name` を変更しても、詳細 AST と Structural Tree の生成ルートが
  同じ規則であること。
- 位置情報がない、または一部しかない入力でも、精密な source map を要求せず
  に扱えること。
- 動的な宣言、参照、ローカルスコープ、mix-in を推測で Structural Tree に追加
  しないこと。
- 深い解析が必要なケースを v2 の詳細 AST へ案内できること。

この確認後に、singleton method のフィールド、superclass のスキーマ、任意の
位置情報、consumer 向けの occurrence 識別子を別の設計変更として決める。
