# 言語プラグイン：責務と提案設計

この文書では、現在の実装と、提案する言語プラグインアーキテクチャを
分けて説明します。提案中の名称は責務の境界を表すものであり、利用可能な
API や、言語を組み合わせて使えることを約束するものではありません。
現在の Ruby フロントエンドのパイプラインについては、[アーキテクチャ](architecture.md)
を参照してください。

## 現在の実装

Lrama は Yacc 文法の解析、文法モデル、規則の準備と展開、LALR/IELR
パーサーテーブルの構築を担います。Arpaka は、文法やテーブルを二重に
実装するのではなく、これらの構造を利用するべきです。生成されたパーサーは
シフト、還元、そして与えられた意味アクションを実行します。

`Lrama::Ruby` は汎用の Ruby 出力バックエンドです。パーサーテーブル、
パーサーランタイム、Ruby の還元アクションを、単独で動作する Ruby ソース
として出力します。現在のアダプターは、アクションの処理を含め、Lrama に
ある C 言語前提を生成用の Ruby Box 内で扱います。上流の Lrama が適切な
拡張 API を提供するまでは、このアダプターを維持してください。プラグイン
の提案は、このアダプターを削除したり、文法とテーブルの責務を Arpaka に
移したりすることを求めるものではありません。

現在、Ruby フロントエンドは `Arpaka::Ruby` と `lib/arpaka/ruby/` の下に
あります。入力された Ruby 文法に対してソースプロファイルを選択し、Action
マッピングを用いて変換し、レクサー、パーサー、Builder、AST ランタイムを
組み立てます。これらの Ruby 固有の意味論は、汎用出力バックエンドとは
分離されています。実験的なサンプルプラグインは、CLI のディスパッチと
生成を独自の Box で行う例を示しますが、汎用的な言語合成プロトコルを
定めるものではありません。

`Arpaka.generate` は単独で動作するソースを返し、`Arpaka.compile` は
インメモリのフロントエンドを提供します。これらの既存エントリーポイントは、
将来のプラグインや、中間的な合成成果物のインターフェースを確定するもの
ではありません。

なお、現在の実装では生成クラス名を `class_name`（CLI では
`--class-name`）で指定でき、Ruby フロントエンドの既定値は `RubyParser` です。
このクラスが生成物のルートになります。

## 提案する責務の境界

| 担当 | 責務 |
| --- | --- |
| Lrama | 文法解析、規則モデルとその準備、パーサーテーブル |
| Lrama 統合層（現在は `Lrama::Ruby` 内） | 上流に適切な拡張 API が存在するまで、Ruby アクションに関する Lrama の C 言語前提を適合させる |
| Arpaka 共通基盤 | Action 参照、共有 Action の配線、汎用 Ruby パーサーの出力、コード生成の調整 |
| `Arpaka::Languages::Ruby`（提案） | Ruby 文法の準備、ソースプロファイル、Action マッピング、フロントエンドランタイム |
| その他の言語実装（提案） | それぞれの文法の準備、プロファイル、意味論、ランタイムコンポーネント |

共通の Action 基盤は、意味値への参照と、共有されるコード生成の仕組みを
扱うべきです。一方で、Ruby の代入、JavaScript の式、テンプレート展開が
何を意味するかを決めるべきではありません。言語ごとの Action マッピングと
Builder がその判断を担います。共有 Action は、実際に挙動が共通する場合に
委譲や Ruby モジュールを通じて再利用できますが、普遍的な意味アクションの
階層や、言語に依存しない IR になる必要はありません。

`Arpaka::Languages::Ruby` は Ruby 言語実装の候補となる場所であり、既存の
置き換え先名前空間ではありません。その文法、プロファイル、アクション、
ランタイムの境界に、Ruby 固有の生成入力と挙動をまとめることを想定します。
ただし、リファクタリング中も現在の `Lrama::Ruby` バックエンド API は維持
します。この表は意図する責務分担を示すものであり、既存バックエンドの
ファイルや名前空間を直ちに移すことを示すものではありません。

## 言語プロトコルと登録

`Arpaka::Language` はプロトコルという概念の名前です。実装は生成処理と
連携し、自身の言語固有の貢献内容を記述できる必要がありますが、
`Arpaka::Language` 基底クラスの継承を必須にすることは、この提案に含まれ
ません。委譲、モジュール、最終的なプロトコルを満たすオブジェクトのいずれも、
実装手段として考えられます。

具体的な登録 API、発見機構、メソッドシグネチャ、中間表現は、まだ決まって
いません。特に、プラグインインターフェースは完成済みのソース文字列だけを
返すものに限定すべきではありません。既存のソース返却 API は引き続き有用
ですが、将来の合成では、最終的なソース出力の前に文法、Action、ランタイム
への貢献が必要になる可能性があります。この文書は、それらの貢献の形式を
選択するものでも、どのように組み合わせるかを規定するものでもありません。

## 名前空間、分離、将来の合成

言語ごとの名前空間は実装を識別し、定数名の衝突を防ぎます。Ruby Box は
ロードと分離を制御します。これらは別々の関心事です。言語名前空間がある
からといって、すべての実装を別々の Box に置かなければならないわけでは
ありません。

将来 `--ast-type structured` のような AST 表現の選択を導入しても、生成物の
ルートは `class_name`（CLI では `--class-name`）で指定したクラスです。
AST の利用側が表現ごとに別のクラス名を指定する必要はありません。
言語実装の名前空間と生成物の配置については、複数言語を併用する際の衝突も
含めて別途検討します。

提案する設計では、協調が必要な複数の名前空間付き実装を、合成用の Box に
ロードできるようにするべきです。JSX や ERB は、その構成を検討するための
動機となる例であり、Arpaka がすでにどちらかの合成をサポートしていると
主張するものではありません。文法の結合、レクサーの協調、意味論上の境界、
貢献内容の形式は、いずれも今後の設計課題です。Box の配置だけでこれらの
問題が解決するわけではありません。

## AST の選択と単独出力

`ast_type` は入力言語とは独立した、出力表現の選択肢を表します。これを
言語セレクターとして使ったり、各言語が AST 表現を一つだけ持つことを
意味したりしてはいけません。これは設計上の境界であり、汎用的な
`ast_type` 選択 API が実装済みであるという主張ではありません。共有の
`Structural Tree` 表現は別の将来課題です。言語プラグインを整理するために、
その定義を先に済ませる必要はありません。

生成時のプラグインや Box を、生成されたフロントエンドのランタイム依存に
してはいけません。既存の単独出力の契約を維持してください。生成される
Ruby ファイルには、パーサー、レクサー、Builder、必要な AST/ランタイム
コンポーネント、メタデータ、ライセンス表示を含めます。Arpaka や Lrama の
gem、インストール済みプラグイン、Ruby Box、補助ファイル、ファイルシステム
への書き込みなしに、呼び出しごとに状態を新しくして解析できなければなり
ません。生成時とインメモリコンパイル時には Box を利用できますが、生成
ファイルを通常どおりロードする際に Box を必要としてはいけません。
